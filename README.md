# cadence · v0.1

设计文档见 `个人AI助手项目设计文档.md`。这里是它第 13 节路线图的阶段 1：
**记饮食 → 查高德拿候选 → 用自己的记录筛 → 推荐**。
没有语音、没有摄像头、没有 agent 框架。

## 开始用

1. 打开 `.env`，把你那家模型的三行取消注释，填上 API KEY
2. 想用地点推荐再加两行（不加也能跑，只是没有 `places.py`）：
   ```
   CADENCE_AMAP_KEY=在 lbs.amap.com 申请，平台类型必须选「Web 服务」
   CADENCE_HOME=经度,纬度        # 用 python3 places.py --where 你家地址 查
   ```
3. `python3 chat.py`

## 命令

```bash
python3 chat.py                                    # 对话（需要 API KEY）

python3 log_meal.py 牛肉面 --note 有点咸            # 记一顿饭
python3 log_meal.py 麻辣烫 --at 12:30
python3 log_meal.py 烤羊腿 --place 随园餐厅          # 记在哪家店吃的

python3 logs.py                                    # 最近 7 天的全部记录（带 id）
python3 logs.py --kind meal --days 30              # 只看吃的
python3 logs.py --category appointment             # 只看和别人有约的
python3 logs.py --status planned                   # 还没做的
python3 logs.py --place 随园餐厅                    # 这个地方的全部记录
python3 logs.py --delete 3                         # 删一条（只有你能删，模型不能）

python3 check.py                                   # 自检：67 条断言，改完 db.py 就跑一次

python3 places.py --types                          # 这一带实际有哪些菜系
python3 places.py 四川菜                            # 查这类店，带上"你去过没有"
python3 places.py 四川菜,湘菜,火锅 --max-cost 60     # 多个关键词、限人均
python3 places.py 火锅 --at 新街口                   # 换个中心点，地址自动转坐标
python3 places.py --where 新街口                    # 只查坐标

python3 remember.py --list                         # 当前有效的记忆
python3 remember.py preference food.dislike.cilantro "不吃香菜"
python3 remember.py constraint diet.goal "在减脂" --expires 90
python3 remember.py --history food.dislike.cilantro   # 一个 key 的全部版本
```

不用模型 API KEY 也能跑除 `chat.py` 外的全部命令（`places.py` 要高德 key）。

## 文件

| 文件 | 作用 |
|---|---|
| `db.py` | **所有读写的唯一入口**。没有 `execute_sql()`，只有具体函数（文档 5.7） |
| `llm.py` | system prompt、工具定义、工具调用循环 |
| `amap.py` | 高德接口。**只回答"附近有什么"**，不含任何个人偏好逻辑 |
| `ui.py` | **跟人确认的唯一入口**。换语音时只改这一个文件 |
| `config.py` / `.env` | 模型和高德的配置。换厂商只改 `.env` |
| `chat.py` | 对话入口 |
| `log_meal.py` / `logs.py` / `remember.py` / `places.py` | 独立 CLI 脚本（文档 8.2） |
| `check.py` | 自检脚本。跑在临时库上，**不碰 `cadence.db`** |
| `cadence.db` | SQLite 单文件。删掉就是重来 |

**`logs` 表用两级分类**，因为"是什么事"和"有没有别人"是正交的两个维度：

| 列 | 取值 |
|---|---|
| `category` | `appointment`（和别人有约）/ `personal`（只关自己） |
| `kind` | `meal` `study` `exercise` `travel` `health` `purchase` `other` |
| `status` | `planned`（还没发生）/ `done` |

约人吃饭 = `appointment` + `meal`，两边都不用让步。

**`status` 只有两个值，不加 `cancelled`（2026-08-12 测过，销案）。**
"黄了"该写进 `note` 而不是变成一个状态值 —— 实测问「有没有谁老放我鸽子」，
模型从 `note` 里读出了谁失的约、什么原因、是取消还是改期，
还正确排除了"我自己放别人鸽子"那次。**一个状态值装不下这些。**

**高德的数据一条都不落库。** 库里只有你自己的东西：吃了什么、在哪吃的、
说过什么。候选集随时能重新拿到，个人记录拿不回来 —— 只有后者值得存。

## 已经定下来的纪律

来自设计文档，现在遵守能省很多事：

- **时间戳一律存 UTC + ISO 8601**，只在显示时转本地时区（5.6）
- **模型只说本地时间，UTC 不出 `db.py`。** 工具参数一律填 `2026-08-10 15:00` 这种本地格式，`db.from_local()` 负责换算。让模型自己算时区，它会算错，而且错了不报错——一个格式不对的字符串塞进 TEXT 列，SQL 比较只会安静地给出错误结果
- **当前时间缀在 user 消息上，不写进 system prompt。** prompt 缓存按前缀匹配，system 在 `messages` 最前面，它每轮一变，整段对话历史全部失配。变化的东西必须待在列表末尾
- **记忆追加不覆盖**，所以 `--history` 查得到"它为什么这么以为"（5.4）
- **`memories.key` 用归一化英文**（`food.dislike.cilantro`），人话放 `value`（5.4）
- **模型只能调窄接口**，不能自己写 SQL（5.7）
- **模型能改不能删。** 删除不可逆、更正可逆，风险差一档，所以删除权留在 CLI 里（5.7）
- **确认只能走 `ui.confirm()`，别在别处写 `input()`。** 写在 system prompt 里的"请先确认"不算数——模型可能不听，而且你查不出为什么（6.1）
- **查不到就说查不到，不编**（7.4）
- **模糊查询的参数要搜完所有可能藏着答案的列。** `find_logs` 的 `keyword` 同时搜
  `name` / `note` / `place` —— 人名几乎只写在备注里，只搜 `name` 的时候，
  「我跟老王出去过几次」会捞到一条然后回答"只有这一次"。**把有的说成没有，
  比编造更难发现，因为它听起来很守规矩**
- **检索的时间窗看有没有关键词，这是代码里的默认值不是提示词。** 给了 `keyword`
  或 `place` 就搜全库（关键词本身就是筛子），没给才限最近 30 天。
  实测五万行三列 `LIKE` 只要 26 毫秒——**贵的从来不是查，是回填进 prompt 的条数**
- **截断了必须说。** `find_logs` 回 60 条封顶，但**总数一起返回**。只截不说，
  模型会拿一个残缺集合下结论，那是"把有的说成没有"的另一种长相（12.1 的熔断）
- **模型的输出是交界处，交界处必须有契约**（12.2）。`llm.py` 的 `_parse_args`
  接住畸形 JSON：能窄修补的修（只补日期缺的引号，且**打印 + 落库**，
  不许静默改模型输出），修不好的如实退回并**指名道姓说错在哪个字段**——
  只说"JSON 不合法"，它会原样再来一遍
- **候选集和判断依据必须分开。** 高德只回答"附近有什么"，"哪家合适"只能由
  `logs` 和 `memories` 回答。让高德评分参与主排序，就是放弃这个项目唯一的优势（7.5）
- **地点是会话状态，用代码兜住，而且必须回显。** 说过"新街口"之后模型可能忘了填
  `near` 就悄悄退回家，而你看不出来——所以 `llm.py` 记住上一个中心点，
  并且每次返回都写明用的是哪儿（6.1 的同一个道理）
- **高德不认得的词要当场丢掉。** 搜「辣的」它不返回 0 条，而是给你八家肯德基。
  乱猜比查不到更危险：查不到你会改词，乱猜你会真把肯德基当辣菜推出去（7.4）
- **地名一律限定城市，并且把解析出的完整地址显示出来。** 不限城市查「新街口」，
  高德给的是**四川乐山**的那个，还不报错。重名是常态不是意外
- **正交的两个维度不许塞进一列。** 分类先按"活动类型"设计过，结果在"约了人一起去
  健身"上碎了 —— 按活动它是健身，按有没有别人它是约，一列装不下两个答案。
  动手前先问：我要分的这几类，会不会有一件事同时属于两类？会就是两列
- **受控词表由代码强制，而且两级取值不许重叠。** 让模型自由填 `kind`，它会造出
  `exam` / `test` / `考试` 三种写法，然后按分类什么都查不全，且一声不吭。
  取值不重叠是"两级填反"唯一可靠的防线 —— 实测模型真的把 `personal` 填进过
  `kind`，因为值域不交叉，校验当场就挡下了，靠注释提醒挡不住
- **空字符串不违反 `NOT NULL`。** SQLite 的 TEXT 列里 `''` 是合法值，
  不显式挡掉，库里就会长出一批 `kind=''` 的行，不报错
- **状态存真相，过期提示渲染时现算。** `status` 落库（写入时由代码从 `ts` 定，
  之后只有人开口才改），"这条早就过了"每次显示时拿当前时钟算一次、不落库。
  所以没有"上次判定到下次判定之间"的空窗 —— 那个问题只属于定时任务写库的方案
- 每次模型调用的 token 数写进 `events` 表 —— 没有账本就没有优化（12.1）
- **加表加列走 `db.py` 的 `NEW_COLUMNS`。** `CREATE TABLE IF NOT EXISTS` 对已存在的表
  不生效，光改 `SCHEMA` 老库不会长出新列。**带非空默认值的 `ADD COLUMN` 会自动
  回填老行**（加 `status` 时现有记录全变 `done`，正好是对的）。改结构前先
  `cp cadence.db` 备份，改完跑 `python3 check.py`

## 已知问题

**地点匹配会误命中（已知，决定先不修）**

`place` 用双向包含匹配，所以短地名会匹配上包含它的店名：库里记了一条
`place=宣城`，推荐时高德返回一家"宣城老鸭汤"，就会被标成"你去过1次"。

不修，也**不用"别填城市"这种规则去绕**——数据该老实记用户说的地方，
出问题的是匹配那段代码，不该让人去迁就它。而且这毛病不是城市带来的：
`place=面馆` 一样会匹配一堆店，双向包含从一开始就有这个性质。

等它真的误报一次再修，那时才知道该按长度、按城市、还是按"去掉括号
后缀再精确匹配"来收紧。现在猜一个补丁上去，只会挡住真命中。
同理，店名里的 `%` 和 `_` 会被 `LIKE` 当通配符，也不加 `ESCAPE`。

**空字符串能绕过确认框（2026-08-12 已修）**

`llm.py` 判断"模型要不要改这个字段"用真假值，`db.correct_log` 用
`is not None`，两边对空串看法不一样，于是一个没经过确认的字段会被改掉。

加 `category` / `status` 时顺手修了：两边统一成 `is not None`，
并且空串当非法输入直接挡回去（"清空"该是显式操作，不是省略参数的副作用）。
留着这一条是因为**教训比 bug 本身重要**——同一个判断散在两个文件里、
用了两种写法，就一定会不一致；加字段时照抄，一个 bug 会变成四个。

**输入偶尔丢字符（不复现，决定不修）**

2026-08-10 出现过一次：终端里输入"我还吃了梅干菜烧肉，复热的时候…"，
到达 Python 的只有"复热的时候…"，前半句丢了，模型只好从上文推断，
把菜名记成了牛肉面。第二天原样再输一遍，正常。

不加防线，因为三种候选都比不加更糟：

- **回显输入** —— 没用。终端本来就在回显，字符在输入法那层丢了就没上过屏
- **检测"句子不完整"** —— 会误伤"对""删了""嗯"这类正常的短输入，天天弹确认
- **禁用 readline** —— 方向键和历史记录会一起没掉

真正的防线是**可查、可见、可改**，这三样已经有了：`events` 记原话、
工具调用当场回显、`correct_log` 能改回来。防不住的故障，保证它可追可修就够了。

再遇到时，这样确认 Python 实际收到了什么（跟屏幕上显示的对不上就是又发生了）：

```bash
sqlite3 cadence.db "SELECT payload FROM events WHERE type='utterance' ORDER BY id DESC LIMIT 5;"
```

**它不会主动提醒你。**

记了"周五去宣城"之后，cadence **不会**到时间叫你——它只是你问起时答得上来，
并且看见过期未确认的记录会顺口问一句"那件事做了没"。

真正的提醒要走设计文档第 6 节的 `nudges` + 闸门（静默时段、同类冷却、
每日预算、过期作废），那是独立的一步。**没有闸门的提醒会平滑地变讨厌，
而且没有哪一天你会察觉到它变糟了**（14.3）。

## 下一步

**阶段 1 齐了，现在开始的两周是判据期。** 不加新功能，就用。

判据是事先写好的，达不到就砍不修：
**我主动用了 ≥10 次，且 ≥3 次真按它说的吃了。**

想让它变准，唯一要做的事是**吃完记一笔，带上店名和一句真话**：

```bash
python3 log_meal.py 烤羊腿 --place 随园餐厅 --note 排队久但值
```

去过的店下次会带着这句话出现在推荐里。记录攒不起来，推荐就只是个搜索框。

现在也能跟它说将来的事了：

```
你：我这周五去宣城找朋友玩，他准备租车带我去泾县转一转
    → appointment / travel，周五，计划中，细节留在 note 里
你：我这周有什么约
你：我还有什么没干        → 过期没确认的会被点出来
```

## 待办

时间线 + 数据库的基本设计已经定型（四批测试没有一条结论要求改表结构）。
下面这些是明确要做、但还没动的。

**A · 归档层：把记录提炼成判断**

不是把原始记录压缩存档，是提炼**结论**：小明三次放鸽子 → 一条记忆
「这个人约人不太靠谱」。一条判断约 15 token，五十条 750 token，付得起。

| 设计点 | 现在的想法 |
|---|---|
| 触发时机 | 每轮 session 结束，归档库里还没归档过的内容 |
| 怎么归 | 另设一个入口 + **另一套系统提示词**——离线批处理不该占对话上下文，也不该用同一套人格 |
| 人来修正 | 对话结束时问"你觉得这个人怎么样"，用户答"他只是神经大条，做大事还是靠谱的"，覆盖模型的判断 |
| 未解决 | 怎么知道"哪些还没归档过"，需要一个游标或标记 |

⚠️ **"对话结束时主动问一句"属于文档 6 的主动性策略层，要走闸门**
（静默时段 / 同类冷却 / 每日预算 / 过期作废）。不能只写一句提示词就上线——
14.3：它烦不烦人决定它活不活下来。

外部参考（2026-08 调研）：这个东西业界有名字，叫 **sleep-time compute**
（[Letta](https://www.letta.com/blog/sleep-time-compute/)）——一个后台 agent 在主 agent
空闲时整理记忆、合并归档。触发点是"主 agent 闲下来了"，不是定时轮询，
跟这里"session 结束时归档"是同一个设计。**产出是判断，不是摘要**——
这一点和 Mem0 的"抽事实"路线一致，和"把原始记录压缩存档"是两回事。

**B · `memories` 的注入与淘汰规则**

- **它不是按需调用的**，是每轮全量注入 system prompt（5.3）。归档一开，它只增不减
- **淘汰机制有，但全押在 `key` 上。** 5.4 的做法是"同 `key` 追加新版本而非覆盖，
  读取取最新未失效的那条"，`active_memories()` 已经这么实现了。
  问题是这套纪律是为**手工录入**定的——人写 key 会下意识复用，
  **模型自动写入时不会**，除非代码逼它复用（见下面第 1 条）
- 用户的修正该以什么形式覆盖模型的判断
- 到多少条该开始筛选，而不是全量注入

外部参考（2026-08 调研）：

**已经做对的两件事，别改动它们：**

- **追加不覆盖。** `active_memories()`（`db.py:491`）按 `key` 取最新未过期的一条，
  表本身只增不改。别人踩的坑正在这里：
  [Mem0 的自动冲突消解会静默 `DELETE`](https://dev.to/mukesh_13/mem0-auto-resolves-memory-conflicts-for-you-until-it-silently-deletes-one-you-still-need-4f4m)——
  不抛异常、不记日志，几周后才以行为异常暴露。**那是 P3「把有的说成没有」的记忆版。**
- **写入留痕。** `events` 表已经是社区给那场事故开的药方（"写操作前后都记日志"）。

**归档要加的三条约束：**

1. **归档必须复用已有的 `key`，不能每次新起一个。**
   淘汰机制全靠 `key` 对得上——`person.xiaoming.reliability` 和
   `person.xiaoming.punctuality` 在人看来是一件事，在 SQL 里是两条永不相互取代的记忆。
   ⚠️ **这是 Mem0 那场事故的镜像**：它把不同 scope 压成一个 key 所以误删，
   cadence 会把一个 scope 拆成多个 key 所以只增不减。方向相反，代价一样。
   所以归档入口要先 `SELECT DISTINCT key`，让模型在现有 key 里挑，挑不到才新建。
2. **提炼时必须保住限定语。** Mem0 那场事故的根因是抽取把 scope 剥掉了：
   "设计评审时偏好异步"和"线上事故时偏好同步"被压成"偏好异步"和"偏好同步"，
   看起来矛盾就删了一条。所以要写「**约人**这件事上不太靠谱」，不能压成「不靠谱」。
3. **撑不住的时候分两层，不是排优先级。** [Letta MemFS](https://docs.letta.com/concepts/memfs)
   把记忆分成 `system/`（每轮注入）和 `reference/`（按需读），目录分层而不是给一张表打分。

**C · 星期换算**（模型会算错，间歇性）

模型交"本周五 09:00"原话，`db.from_local()` 算日期；`_fmt_log` 回显带上星期。
**算术收进代码**，跟 5.6 处理时区是同一个做法。

**D · 重复性事件**（"以后每周三都有"现在会降级成一条单次记录）

**E · 其他**

- 高德那条慢路（"今天吃什么"要拉全量，四到六秒）——只缓存那一行分类目录就能解决
- 通用的写入 CLI（`log.py`）——现在非饮食记录只能从对话写
- 攒够一批 `kind=other` 之后，看它们该拆成什么新分类
- 拿纯 md 文档替代 `logs` 表能做到什么程度，值得试一次做对照

```bash
cp cadence.db ~/cadence-backup-$(date +%F).db
```

文档 3.1：定时 `cp` 到另一块盘即备份。不需要比这更复杂的东西。
